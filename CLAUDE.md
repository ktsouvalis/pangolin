# CLAUDE.md

Guidance for working in this repo.

## What this is

Two standalone Textual TUI scripts for monitoring a **Pangolin HA Cluster** (University of Peloponnese — Digital Governance Unit). No shared package, no build step — each script is a single file, run directly with `python3`.

- `monitor.py` — live dashboard, one panel per service (Keepalived/VIP, Pangolin/Gerbil, HAProxy, Patroni/PostgreSQL, etcd, Newt agents), polls on a timer.
- `logs_viewer.py` — pulls WARN/ERROR logs over SSH from every node (`docker logs` or `journalctl`), plus resolved Newt ACCESS session logs. Has a TUI mode and a `--save` mode that writes files instead.
- `create_private_resources.py` — batch-creates Pangolin private (site) resources from a filled-in xlsx request sheet via Pangolin's **Integration API**. Each **User Emails** entry on a row becomes its **own** site resource (a row with 3 emails creates 3 resources), each spanning every site in the org (via the API's `siteIds` array — the older per-site `siteId` field is deprecated), so it's reachable through any site's tunnel for HA. Resource names are computed, not user-entered: `<city>-<username>-<vlan>[-<z>]`, where `Name` holds the city, `username` is the email's local part with any `.` stripped (e.g. `m.katsis` → `mkatsis`), and `vlan`/`z` come from the Destination's `10.x.y.z` octets (`y` zero-padded to 2 digits, `z` not padded, `z` dropped for CIDR rows) — e.g. `ktsouvalis@uop.gr` at `10.23.2.50`, city "Patra" → `patra-ktsouvalis-2302-50`. As of 2026-07-30, the resource's `niceId` is also set explicitly rather than left to Pangolin's own random generation on create: `<username>-<vlan>[-<z>]-<ports>`, `ports` being the row's TCP `Ports` numerically sorted, each prefixed with "p" and dash-joined (e.g. `ktsouvalis-2302-50-p22-p3389`) — `niceId` never carries the city segment `name` does. An email that doesn't match any current org user still gets its resource created (as of 2026-07-29 — name/niceId computed the same way regardless, since neither depended on the user lookup) but with no user attached, reported as `OK_NO_USER`/`DRY-RUN_NO_USER` rather than skipped; `normalize_private_resources.py` backfills access for these later once the account exists. Not a TUI; one-shot CLI with a `--dry-run` mode. Writes a `_results_<timestamp>.xlsx` report next to the input file (adds/replaces a "Results" sheet).
- `normalize_private_resources.py` — audits *existing* Pangolin private resources (fetched live via the Integration API, not from a spreadsheet) against that same naming convention, extended to cover CIDR resources too (`<city>-<username>-<vlan>-<tail>`, `tail` = `all` for a `/24`, else the literal prefix length, e.g. `16`), and prunes any resource down to the single user named in it. As of 2026-07-30, it also audits/fixes `niceId` the same way `create_private_resources.py` computes it (`<username>-<vlan>-<tail>-<ports>`, ports read from the resource's own `tcpPortRangeString`, numerically sorted, each prefixed with "p" and dash-joined, e.g. `p22-p3389`) — this is how the historically-random `niceId`s that predate that script's change get normalized to the deterministic scheme; skipped (niceId left untouched, other fixes still applied) when `tcpPortRangeString` isn't a plain numeric list (e.g. a `*` wildcard or a range). Defaults to a dry run; `--apply` (with a confirmation prompt unless scoped with `--resource-id` or passed `--yes`) makes the changes for real. Never guesses a new access grant from a loose match — a resource with 2+ users where none match a name segment is reported SKIPPED for manual review rather than acted on. The one exception (as of 2026-07-29, extended 2026-07-30 to also try the `niceId` reversal when the name-based one fails): a resource with 0 assigned users whose name **or** niceId is an *exact* reconstruction of its respective naming convention (known city+vlan/tail for name, known vlan/tail/ports for niceId, with exactly one org user's sanitized local part left over either way) is auto-resolved and granted access (`action=grant_access`) — this is the reverse of `create_private_resources.py`'s `OK_NO_USER` case, not a guess, since it's the literal inverse of that script's own naming formulas. Anything looser than an exact match still falls back to SKIPPED with a best-effort suggestion. Writes its own `private_resources_normalize_<timestamp>.xlsx` report (git-ignored like the others).

Both TUI scripts read the same `config.yml` (see `config.yml.example` for the schema — node IPs/names per group, ports, SSH creds, credentials, `services:` list for the log viewer). `create_private_resources.py` reads the same file's `pangolin:` block (`base_url`, `org_slug`, `api_key`) — see the "Pangolin Integration API" section below, this is **not** the same thing as the dashboard/monitoring endpoints the other two scripts hit.

## Layout

- `monitor.py`, `logs_viewer.py`, `create_private_resources.py`, `normalize_private_resources.py` — the four tools, no other source files.
- `pangolin_private_resources_template.xlsx` — the request-sheet template for `create_private_resources.py` (columns, in this exact order since the script parses by position not header name: Name, Destination, Ports, Alias, User Emails, Notes; see its own instructions tab — currently in Greek, "Οδηγίες"). The `Operation System` column was removed from the template as of 2026-07-30 (it had already gone informational-only on 2026-07-29 once the fixed OS-based port policy was reversed) — `create_private_resources.py` was updated to match, dropping the column from its positional unpack (now 6 fields, not 7) and from the request/report payloads entirely. The `Name` column is filled in by the Digital Governance Unit (not the requester) with the **city**, which feeds the computed resource name — see the `create_private_resources.py` bullet above. Filled-in request/report xlsx files are git-ignored (`*.xlsx` except `*template.xlsx`) since they carry real internal IPs/emails — don't fight that with `git add -f`.
- `config.yml.example` — schema reference; `config.yml` is the real, git-ignored, credential-bearing file.
- `requirements.txt` — pinned deps (note: `redis` is listed and `redis_timeout` exists in the config schema, but no code currently uses redis — leftover, not a bug to "fix" by wiring it up).
- No tests, no CI, no linter config.

## Pangolin Integration API (server-side, not this repo)

`create_private_resources.py` talks to Pangolin's **Integration API**, which is a separate, opt-in service — not the same backend as the dashboard (`pangolin.uop.gr/api/v1/...`, session-cookie based) or the `:3001` health endpoint the monitoring scripts use. It must be explicitly enabled per-node in Pangolin's own `config.yml` (at `/opt/pangolin/config/config.yml` inside the `pangolin` container, **not** this repo's `config.yml`):

```yaml
flags:
    enable_integration_api: true
server:
    integration_port: 3003   # default
```

...and exposed through Traefik (`/opt/pangolin/config/traefik/dynamic_config.yml`) via a dedicated router. This cluster exposes it at `https://pangolin.uop.gr/int-api` (path-based on the existing domain/cert, with a `stripPrefix` middleware) rather than the docs' example of a separate subdomain, to avoid provisioning new DNS/TLS. Hence `config.yml`'s `pangolin.base_url` here is `.../int-api`, not `.../api`.

**As of 2026-07-08, this is applied on all 3 nodes** (node 1 was rolled out last, once it came back from a genset maintenance window that had made it briefly unreachable). Verified working with each node holding the VIP in turn, including node 1 reclaiming MASTER (priority 100) after rejoining.

Each Pangolin node's `config.yml`/`dynamic_config.yml` are independent, per-node files (no shared filesystem) — any change here must be replicated to all three and containers restarted one at a time (VIP fails over to the others during each restart). **Restart the `pangolin`/`traefik` containers directly (`docker restart pangolin`, `docker restart traefik`) rather than via `docker compose restart` from `/home/ktsouvalis/docker-compose.yml`** — that file declares `name: pangolin`, which only matches the live Komodo-managed project on some nodes (project name `pangolin`) and not others (e.g. node 1's project is named `pangolin-node-1`). On a project-name mismatch, `docker compose restart` silently no-ops (exits 0, prints nothing, container uptime doesn't change) instead of erroring, so always confirm a restart actually happened via `docker inspect <container> --format '{{.State.StartedAt}}'` before assuming it worked.

## Working in this repo

- Config-driven by design: adding/removing a node or service should never require touching the Python — check `config.yml.example` for the right schema shape before adding new fields to the scripts.
- Both scripts tolerate `nodes.newt` being either a plain list or `{ssh: {...}, hosts: [...]}` (per-group SSH override). If you touch node-group parsing, preserve that shape in both files — they duplicate this logic (see `monitor.py`'s `_newt_raw` handling and `logs_viewer.py`'s `get_nodes`/`get_ssh_creds`).
- Health checks favor inference over new dependencies where there's no clean API: Gerbil and Keepalived health are both inferred from the Pangolin API endpoint rather than adding SSH/docker-inspect checks. Follow that pattern rather than introducing a heavier check unless asked.
- `_UNICODE`/bullet handling in `monitor.py` exists because some Proxmox CTs lack a UTF-8 locale — don't remove the ASCII fallback.
- Panels in `monitor.py` are conditionally shown only when their node group is non-empty (see `if NEWT_NODES:` in `compose`/`on_mount`/`_apply_updates`) — new optional panels should follow that pattern rather than always rendering.
- `README.md` is the user-facing doc; keep it in sync when adding panels, CLI flags, or output files (e.g. the `_newt.csv` side-output from `--save` mode).
- `create_private_resources.py` always sends `roleIds: []` and grants access only via a resolved single `userIds` entry per resource — that's deliberate (per-resource, per-user, email-based allowlists, no role-based access), not a gap to fill in. An unresolved email still creates its resource (as of 2026-07-29), just with `userIds: []` and status `OK_NO_USER`/`DRY-RUN_NO_USER` instead of `OK`/`DRY-RUN` — it is not a local FAIL, since the naming never depended on the user lookup succeeding. Only invalid `Ports`/`Destination` values still fail a row locally before any API call. `normalize_private_resources.py` is what backfills the missing user later, once the account exists — see its bullet below.
- `create_private_resources.py`'s TCP ports come from the request sheet's `Ports` column (comma-separated port numbers, e.g. `22,3389`), user-entered per row — this reverses the earlier (2026-07-08) fixed OS-based port policy (as of 2026-07-29). UDP and ICMP are still always blocked for every resource and are not user-configurable. The `Operation System` column itself was removed from the template on 2026-07-30, and the script no longer reads or reports it in any form. A missing/blank `Ports` value or any non-numeric token fails that row locally before any API call.
- `create_private_resources.py` only supports creating site resources today — updating an existing one (e.g. looked up by the `niceId` shown in a prior Results sheet) is a planned TODO (see the comment above `main()`). Note the API's update/delete routes are keyed by the numeric `siteResourceId`, not `niceId` — a niceId-based `--update` mode would need to resolve niceId → siteResourceId first via `GET /org/{orgId}/site-resources`. `normalize_private_resources.py` now implements the rename half of that TODO (`POST /site-resource/{siteResourceId}`) for the specific case of enforcing the naming convention on existing resources (both `name` and, as of 2026-07-30, `niceId` — merged into a single POST call via `update_resource()` when both need fixing) — it's not a general-purpose `--update` mode.
- The Integration API accepts an explicit `niceId` on both create (`PUT /org/{orgId}/site-resource`) and update (`POST /site-resource/{siteResourceId}`, which additionally constrains it server-side to `^[a-zA-Z0-9-]+$`) — confirmed via the swagger schema (see the bullet below on finding it), not documented in prose anywhere. That's what let `create_private_resources.py` stop relying on Pangolin's own random niceId generation, and let `normalize_private_resources.py` rename existing ones to match.
- The Integration API's Swagger spec isn't reachable through this cluster's `/int-api` path prefix (only the routes Traefik forwards are exposed) — to find undocumented site-resource endpoints (`GET/POST /site-resource/{id}/users`, `/roles`, `/clients`, and their `/add`/`/remove` variants), fetch `https://api.pangolin.net/v1/docs/swagger-ui-init.js` (the hosted instance's docs, same codebase) and extract the embedded `swaggerDoc` JSON — the rendered Swagger UI page itself has no static HTML content to scrape.
- Every private resource observed in this org (both hand-created legacy ones and ones `create_private_resources.py` made) carries the org's baseline `Admin` role and zero clients, despite `create_private_resources.py` always sending `roleIds: []` — this looks like server-side default behavior, not per-resource state either script manages. `normalize_private_resources.py` reads roles/clients for its report but deliberately never touches them; flag it as a genuine anomaly (not a bug to silently "fix") if a resource ever shows something else.
- `normalize_private_resources.py`'s 0-user auto-resolve (`resolve_unassigned_target` in the script) only fires when peeling the *known* city (name's own first segment) and *known* vlan/tail (computed from the destination, independent of the name) off the resource's current name leaves exactly one org user's sanitized local part — i.e. the name must already be an exact convention match. As of 2026-07-30, if that fails it also tries `resolve_unassigned_target_from_nice_id`, the mirror-image reversal of the niceId's own formula (peels the *known* vlan/tail and the resource's *known* ports — from its own `tcpPortRangeString` — off the *end* of niceId, since niceId has no city segment to anchor a prefix peel). It intentionally does not reuse the looser "any name segment matches a sanitized local part" heuristic (`resolve_target`'s suggestion logic) for auto-apply, since that heuristic is meant only to produce a suggestion for a human to confirm, not to silently grant access. If you extend this, keep that distinction — auto-apply needs the strict exact-reconstruction path (by name or by niceId), not the loose suggestion path.

## Environment

Dependencies live in the `pangolin` conda env (`/home/ktsouvalis/miniconda3/envs/pangolin`), not system/user Python. Run scripts with that env's interpreter (e.g. `/home/ktsouvalis/miniconda3/envs/pangolin/bin/python3 monitor.py`, or `conda run -n pangolin python3 ...` / after `conda activate pangolin`). If a new dependency is needed, install it into that env (`conda run -n pangolin pip install <pkg>`) — never `pip install` system-wide or `--user`.

## Testing changes

No automated tests. Verify by running against a real or representative `config.yml`, using the `pangolin` conda env:
```bash
conda run -n pangolin python3 monitor.py
conda run -n pangolin python3 logs_viewer.py
conda run -n pangolin python3 logs_viewer.py --save /tmp/test_logs
conda run -n pangolin python3 create_private_resources.py pangolin_private_resources_template.xlsx --dry-run
conda run -n pangolin python3 normalize_private_resources.py
```
`config.yml` requires live cluster network access (HTTP endpoints + SSH) to exercise fully; without it, checks will just show DOWN/UNREACHABLE, which is still useful for confirming the UI doesn't crash. `create_private_resources.py --dry-run` still needs a reachable Pangolin API + valid `api_key` (it verifies the org and lists sites/users before dry-running the row parsing). `normalize_private_resources.py` defaults to a dry run already (no `--dry-run` flag needed) — always sanity-check its report before ever passing `--apply` on the full, unscoped resource set; use `--resource-id` to try a live `--apply` against one or two resources first.
