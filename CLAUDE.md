# CLAUDE.md

Guidance for working in this repo.

## What this is

Two standalone Textual TUI scripts for monitoring a **Pangolin HA Cluster** (University of Peloponnese — Digital Governance Unit). No shared package, no build step — each script is a single file, run directly with `python3`.

- `monitor.py` — live dashboard, one panel per service (Keepalived/VIP, Pangolin/Gerbil, HAProxy, Patroni/PostgreSQL, etcd, Newt agents), polls on a timer.
- `logs_viewer.py` — pulls WARN/ERROR logs over SSH from every node (`docker logs` or `journalctl`), plus resolved Newt ACCESS session logs. Has a TUI mode and a `--save` mode that writes files instead.
- `create_private_resources.py` — batch-creates Pangolin private (site) resources from a filled-in xlsx request sheet via Pangolin's **Integration API**. Each **User Emails** entry on a row becomes its **own** site resource (a row with 3 emails creates 3 resources), each spanning every site in the org (via the API's `siteIds` array — the older per-site `siteId` field is deprecated), so it's reachable through any site's tunnel for HA. Resource names are computed, not user-entered: `<city>-<username>-<vlan>-<tail>`, where `Name` holds the city, `username` is the email's local part with any `.` stripped (e.g. `m.katsis` → `mkatsis`), and `vlan`/`tail` come from the Destination's `10.x.y.z` octets/prefix (host: `vlan` = `x`+zero-padded `y`, `tail` = unpadded `z`; CIDR: `vlan` built from whichever octets the prefix fixes, `tail` `all` for a `/24` or the literal prefix length otherwise — identical rule to `normalize_private_resources.py`'s, both scripts duplicate this logic on purpose, see its own file) — e.g. `ktsouvalis@uop.gr` at `10.23.2.50`, city "Patra" → `patra-ktsouvalis-2302-50`. `niceId` was briefly set explicitly on create (2026-07-30), reverted 2026-07-31 (left to Pangolin's random generation, specifically so a still-random niceId could signal "nobody's assigned yet"), and **as of 2026-08-04 set explicitly again for good** — once Pangolin exposed a per-resource `enabled` switch, that random-niceId trick was no longer needed (`enabled` is the explicit signal now, see below), so niceId is computed the same deterministic way `normalize_private_resources.py` always has (`<username>-<vlan>-<tail>-<ports>`) regardless of whether the email resolves to a current org user — the username segment only ever needed the raw email string. An email that doesn't match any current org user still gets its resource created (as of 2026-07-29 — name/niceId computed the same way regardless, since neither ever depended on the user lookup) but with no user attached and **`enabled: false`** (as of 2026-08-04 — its baseline Admin-role default access shouldn't be reachable by anyone until it has a real owner), reported as `OK_NO_USER`/`DRY-RUN_NO_USER` rather than skipped; `normalize_private_resources.py` backfills access and flips `enabled` on for these later once the account exists. Not a TUI; one-shot CLI with a `--dry-run` mode. Writes a `_results_<timestamp>.xlsx` report next to the input file (adds/replaces a "Results" sheet), including `Nice ID` and `Enabled` columns now shown on a dry run too (both are known before any API call).
- `normalize_private_resources.py` — audits *existing* Pangolin private resources (fetched live via the Integration API, not from a spreadsheet) against that same naming convention, extended to cover CIDR resources too (`<city>-<username>-<vlan>-<tail>`, `tail` = `all` for a `/24`, else the literal prefix length, e.g. `16`). As of 2026-07-30, it also audits/fixes `niceId` the same way `create_private_resources.py` computes it (`<username>-<vlan>-<tail>-<ports>`, ports read from the resource's own `tcpPortRangeString`, numerically sorted, each prefixed with "p" and dash-joined, e.g. `p22-p3389`) — as of 2026-08-04 `create_private_resources.py` also sets this on create (see above), so this script is the enforcer/fallback for every resource regardless of origin rather than the *only* place niceId is ever computed; it's still what a hand-created or legacy resource (never touched by `create_private_resources.py` at all) relies on to get a correct name/niceId/enabled state for the first time. As of 2026-08-04, it also audits/fixes the `enabled` switch: a 0-user resource that still can't resolve a target stays (or becomes) disabled (`action=disable_no_user`); a resource that resolves a target — via the 0-user grant, an already-correct single assignment, or a 2+-user primary — becomes enabled (`action` includes `enable`) if it wasn't already. 2+-user AMBIGUOUS resources are left alone on this axis (they already have someone's access, just no resolvable primary). Skipped (niceId left untouched, other fixes still applied) when `tcpPortRangeString` isn't a plain numeric list (e.g. a `*` wildcard or a range). Defaults to a dry run; `--apply` (with a confirmation prompt unless scoped with `--resource-id` or passed `--yes`) makes the changes for real.
  - **0 assigned users**: resolved (`action=grant_access`, plus `enable` if it was disabled) when the name or niceId is an *exact* reconstruction of its respective naming convention (known city+vlan/tail for name, known vlan/tail/ports for niceId, exactly one org user's sanitized local part left over either way — the literal reverse of `create_private_resources.py`'s own naming formulas, not a guess; as of 2026-07-29, extended 2026-07-30 to try both the name and niceId reversal). As of 2026-07-31, if *both* exact reconstructions fail, it also falls back to `find_unique_segment_match()` — exactly one org user's sanitized local part appears as *any* standalone `-`-segment of the name, not necessarily in the specific position the exact reconstructions require. This catches legacy hand-created resources whose names don't fit the computed city+vlan/tail shape at all (this heuristic previously only ever produced a manual-review *suggestion*, via `resolve_target`, never an auto-grant — see the git history on this file before 2026-07-31 if you need the old, more conservative behavior). Still never grants on an actually ambiguous match (zero or 2+ org users matching) — falls back to SKIPPED with a best-effort suggestion either way, and as of 2026-08-04, `action=disable_no_user` if it isn't already disabled (its default Admin-role access shouldn't be live while unowned).
  - **2+ assigned users**: resolved only if exactly one has a sanitized email matching a name segment (identifying a primary owner among several grantees); otherwise SKIPPED as ambiguous (this script has no way to pick a primary among equals, and deliberately doesn't guess). As of 2026-07-31, the *other* assigned users are no longer just pruned off when a primary is found — each one with a resolvable email/userId gets **split off into their own new resource** (`create_split_resource()`: same destination/ports/alias as the original, spanning every org site — matching `create_private_resources.py`'s own HA rationale — named and niceId'd for just them, niceId set immediately since the target is already fully resolved at that point, unlike create_'s xlsx flow) before the original gets pruned down to the primary. A user with no resolvable email (seen on some legacy resources) has nothing to split to and is still just dropped. **Splits happen before the prune**, and if creating any split resource fails, the original resource's access is left untouched entirely — never partially pruned with an assigned user's access nowhere to be found.
  - **Confirmed live API behavior, not documented anywhere in prose:** a `POST /site-resource/{id}` update that omits `tcpPortRangeString`/`udpPortRangeString`/`disableIcmp` doesn't leave them alone — it resets `udpPortRangeString` from blocked back to `*` (all) on the resource being edited. Every update this script issues (rename, niceId fix, or both) explicitly re-asserts the resource's own current values for these three fields for exactly this reason (as of 2026-07-31) — do not "simplify" the update payload by dropping them, even though this script never intends to touch ports/ICMP itself.
  - Writes its own `private_resources_normalize_<timestamp>.xlsx` report (git-ignored like the others).

Both TUI scripts read the same `config.yml` (see `config.yml.example` for the schema — node IPs/names per group, ports, SSH creds, credentials, `services:` list for the log viewer). `create_private_resources.py` reads the same file's `pangolin:` block (`base_url`, `org_slug`, `api_key`) — see the "Pangolin Integration API" section below, this is **not** the same thing as the dashboard/monitoring endpoints the other two scripts hit.

## Layout

- `monitor.py`, `logs_viewer.py`, `create_private_resources.py`, `normalize_private_resources.py` — the four tools, no other source files.
- `pangolin_private_resources_template.xlsx` — the request-sheet template for `create_private_resources.py` (columns, in this exact order since the script parses by position not header name: Name, Destination, Ports, Alias, User Emails, Notes; see its own instructions tab — currently in Greek, "Οδηγίες"). The `Operation System` column was removed from the template as of 2026-07-30 (it had already gone informational-only on 2026-07-29 once the fixed OS-based port policy was reversed) — `create_private_resources.py` was updated to match, dropping the column from its positional unpack (now 6 fields, not 7) and from the request/report payloads entirely. The `Name` column is filled in by the Digital Governance Unit (not the requester) with the **city**, which feeds the computed resource name — see the `create_private_resources.py` bullet above. Filled-in request/report xlsx files are git-ignored (`*.xlsx` except `*template.xlsx`) since they carry real internal IPs/emails — don't fight that with `git add -f`.
- `config.yml.example` — schema reference; `config.yml` is the real, git-ignored, credential-bearing file.
- `requirements.txt` — pinned deps (note: `redis` is listed and `redis_timeout` exists in the config schema, but no code currently uses redis — leftover, not a bug to "fix" by wiring it up).
- No tests, no CI, no linter config.

## Pangolin Integration API (server-side, not this repo)

`create_private_resources.py` talks to Pangolin's **Integration API**, which is a separate, opt-in service — not the same backend as the dashboard (`pangolin.uop.gr/api/v1/...`, session-cookie based) or the `:3001` health endpoint the monitoring scripts use. It must be explicitly enabled per-node in Pangolin's own `config.yml` (at `/opt/pangolin/config/config.yml` inside the `pangolin` container, **not** this repo's `config.yml`):

```yaml
flags:
    enable_integration_api: true
server:
    integration_port: 3003   # default
```

...and exposed through Traefik (`/opt/pangolin/config/traefik/dynamic_config.yml`) via a dedicated router. This cluster exposes it at `https://pangolin.uop.gr/int-api` (path-based on the existing domain/cert, with a `stripPrefix` middleware) rather than the docs' example of a separate subdomain, to avoid provisioning new DNS/TLS. Hence `config.yml`'s `pangolin.base_url` here is `.../int-api`, not `.../api`.

**As of 2026-07-08, this is applied on all 3 nodes** (node 1 was rolled out last, once it came back from a genset maintenance window that had made it briefly unreachable). Verified working with each node holding the VIP in turn, including node 1 reclaiming MASTER (priority 100) after rejoining.

Each Pangolin node's `config.yml`/`dynamic_config.yml` are independent, per-node files (no shared filesystem) — any change here must be replicated to all three and containers restarted one at a time (VIP fails over to the others during each restart). **Restart the `pangolin`/`traefik` containers directly (`docker restart pangolin`, `docker restart traefik`) rather than via `docker compose restart` from `/home/ktsouvalis/docker-compose.yml`** — that file declares `name: pangolin`, which only matches the live Komodo-managed project on some nodes (project name `pangolin`) and not others (e.g. node 1's project is named `pangolin-node-1`). On a project-name mismatch, `docker compose restart` silently no-ops (exits 0, prints nothing, container uptime doesn't change) instead of erroring, so always confirm a restart actually happened via `docker inspect <container> --format '{{.State.StartedAt}}'` before assuming it worked.

## Working in this repo

- Config-driven by design: adding/removing a node or service should never require touching the Python — check `config.yml.example` for the right schema shape before adding new fields to the scripts.
- Both scripts tolerate `nodes.newt` being either a plain list or `{ssh: {...}, hosts: [...]}` (per-group SSH override). If you touch node-group parsing, preserve that shape in both files — they duplicate this logic (see `monitor.py`'s `_newt_raw` handling and `logs_viewer.py`'s `get_nodes`/`get_ssh_creds`).
- Health checks favor inference over new dependencies where there's no clean API: Gerbil and Keepalived health are both inferred from the Pangolin API endpoint rather than adding SSH/docker-inspect checks. Follow that pattern rather than introducing a heavier check unless asked.
- `_UNICODE`/bullet handling in `monitor.py` exists because some Proxmox CTs lack a UTF-8 locale — don't remove the ASCII fallback.
- Panels in `monitor.py` are conditionally shown only when their node group is non-empty (see `if NEWT_NODES:` in `compose`/`on_mount`/`_apply_updates`) — new optional panels should follow that pattern rather than always rendering.
- `README.md` is the user-facing doc; keep it in sync when adding panels, CLI flags, or output files (e.g. the `_newt.csv` side-output from `--save` mode).
- `create_private_resources.py` always sends `roleIds: []` and grants access only via a resolved single `userIds` entry per resource — that's deliberate (per-resource, per-user, email-based allowlists, no role-based access), not a gap to fill in. An unresolved email still creates its resource (as of 2026-07-29), just with `userIds: []` and status `OK_NO_USER`/`DRY-RUN_NO_USER` instead of `OK`/`DRY-RUN` — it is not a local FAIL, since the naming never depended on the user lookup succeeding. Only invalid `Ports`/`Destination` values still fail a row locally before any API call. `normalize_private_resources.py` is what backfills the missing user later, once the account exists — see its bullet below.
- `create_private_resources.py`'s TCP ports come from the request sheet's `Ports` column (comma-separated port numbers, e.g. `22,3389`), user-entered per row — this reverses the earlier (2026-07-08) fixed OS-based port policy (as of 2026-07-29). UDP and ICMP are still always blocked for every resource and are not user-configurable. The `Operation System` column itself was removed from the template on 2026-07-30, and the script no longer reads or reports it in any form. A missing/blank `Ports` value or any non-numeric token fails that row locally before any API call.
- `create_private_resources.py` only supports creating site resources today — updating an existing one (e.g. looked up by the `niceId` shown in a prior Results sheet) is a planned TODO (see the comment above `main()`). Note the API's update/delete routes are keyed by the numeric `siteResourceId`, not `niceId` — a niceId-based `--update` mode would need to resolve niceId → siteResourceId first via `GET /org/{orgId}/site-resources`. `normalize_private_resources.py` now implements the rename half of that TODO (`POST /site-resource/{siteResourceId}`) for the specific case of enforcing the naming convention on existing resources (both `name` and `niceId`, merged into a single POST call via `update_resource()` when both need fixing) — it's not a general-purpose `--update` mode. As of 2026-07-31, it also creates brand-new resources itself (`create_split_resource()`, `PUT /org/{orgId}/site-resource` — the same endpoint and shape `create_private_resources.py` uses) when splitting a multi-user resource apart; still not a general `--update`/`--create` mode, just this one specific case.
- The Integration API accepts an explicit `niceId` on both create (`PUT /org/{orgId}/site-resource`) and update (`POST /site-resource/{siteResourceId}`, which additionally constrains it server-side to `^[a-zA-Z0-9-]+$`) — confirmed via the swagger schema (see the bullet below on finding it), not documented in prose anywhere. `create_private_resources.py` briefly used this to stop relying on Pangolin's own random niceId generation (2026-07-30), reverted (2026-07-31, see the file's own header comment) so a still-random niceId could double as an "unassigned" signal, then **as of 2026-08-04 set it explicitly again for good** once the `enabled` switch (see below) made that trick unnecessary — both scripts now compute the exact same deterministic niceId formula, `create_private_resources.py` on every create and `normalize_private_resources.py` as the ongoing enforcer/fallback (existing resources, splits, and anything `create_private_resources.py` never touched).
- **`enabled` (added in Pangolin 1.21.1, wired up 2026-08-04):** a per-resource switch, used here as the explicit "does this resource have a real, resolvable owner yet" signal — replacing the old random-niceId trick above. `create_private_resources.py` sets it directly from whether the row's email resolved to a current org user (`true` if matched, `false` for `OK_NO_USER`/`DRY-RUN_NO_USER` rows and for `create_split_resource()`'s always-resolved splits it's unconditionally `true`). `normalize_private_resources.py` is the ongoing enforcer: disables a still-unresolved 0-user resource that isn't already disabled (`action=disable_no_user` — closes the gap where an unowned resource would otherwise still be reachable via the baseline Admin role, see the roles/clients bullet above), and enables any resource that resolves a target (0-user grant, already-correct single assignment, or 2+-user primary) if it wasn't already (`action` includes `enable`). Ambiguous 2+-user resources are left alone on this axis — they already have someone's real access, `enabled` only ever tracks the 0-user axis. **Confirmed live 2026-08-04** (`--apply` run against the real cluster, 153 resources): the field is literally named `enabled`, and `action=disable_no_user` correctly flipped 27 genuinely-unowned resources off; a follow-up dry run confirmed they stayed disabled (idempotent, no repeat action) and every other resource needed no `enabled` change. `enabled` is still always explicitly re-asserted on every update this script issues rather than left to an implicit default, same precautionary pattern as `tcpPortRangeString`/`udpPortRangeString`/`disableIcmp` below — that part remains a precaution, not a confirmed-necessary workaround (unlike the tcp/udp/icmp gotcha, omitting `enabled` on an update hasn't actually been tested).
- The Integration API's Swagger spec isn't reachable through this cluster's `/int-api` path prefix (only the routes Traefik forwards are exposed) — to find undocumented site-resource endpoints (`GET/POST /site-resource/{id}/users`, `/roles`, `/clients`, and their `/add`/`/remove` variants), fetch `https://api.pangolin.net/v1/docs/swagger-ui-init.js` (the hosted instance's docs, same codebase) and extract the embedded `swaggerDoc` JSON — the rendered Swagger UI page itself has no static HTML content to scrape.
- Every private resource observed in this org (both hand-created legacy ones and ones `create_private_resources.py` made) carries the org's baseline `Admin` role, despite `create_private_resources.py` always sending `roleIds: []` — server-side default behavior, not per-resource state either script manages. **Confirmed live 2026-08-04, direct `GET /site-resource/{id}/roles` call:** this comes back as the *same* role object (`roleId: 1, name: "Admin", isAdmin: true`) listed **twice**, not two different roles — `isAdmin: true` marks it as Pangolin's built-in super-admin role, which is why it never shows up under a resource's own Roles tab in the dashboard UI (it was never really "assigned" the way an explicit grant would be). `normalize_private_resources.py` treats any number of repeated `"Admin"`-only entries as this same expected baseline and only flags a genuinely different role name as an anomaly (never auto-fixed either way). `clients` (`GET /site-resource/{id}/clients`) is confirmed always `[]` for every resource in this org — as of 2026-08-04 it's no longer reported/checked at all (still fetched internally, purely to echo `clientIds` back unchanged on updates, same as tcp/udp/icmp).
- `normalize_private_resources.py`'s 0-user resolve (`resolve_unassigned_target` in the script) fires when peeling the *known* city (name's own first segment) and *known* vlan/tail (computed from the destination, independent of the name) off the resource's current name leaves exactly one org user's sanitized local part — i.e. the name is an exact convention match. If that fails, it also tries `resolve_unassigned_target_from_nice_id`, the mirror-image reversal of the niceId's own formula (peels the *known* vlan/tail and the resource's *known* ports — from its own `tcpPortRangeString` — off the *end* of niceId, since niceId has no city segment to anchor a prefix peel). **As of 2026-07-31**, if *both* of those fail, it now also tries `find_unique_segment_match()` — the same "any `-`-segment matches exactly one org user" heuristic that used to be `resolve_target`'s manual-review-only suggestion, promoted here to an actual auto-grant for the 0-user case specifically (still gated on a unique match; a genuinely ambiguous segment match is still just a suggestion, never auto-applied — see the 2+ user case, which still calls `resolve_target` directly and never `find_unique_segment_match`). If you're reading old context (a previous version of this file, or an old commit message) that says this distinction is deliberately *not* crossed — that changed on 2026-07-31 at the repo owner's explicit request; the loose heuristic is now trusted for the 0-user case precisely because it's still unique-match-gated, not because the gate was removed.
- `normalize_private_resources.py`'s 2+ user handling (as of 2026-07-31): once a primary owner is resolved (exactly one assigned user's sanitized email matches a name segment), every *other* assigned user with a resolvable email/userId is split off into their own new resource (`create_split_resource()`) rather than dropped when the original gets pruned to the primary — see `process_resource()`'s `split_off_users`/`unsplittable_users` locals. Splits are created *before* the original is touched; if any split fails, the original's access is left exactly as it was (no partial state where someone's access was pruned but their replacement resource doesn't exist). A user with no resolvable email can't be split to anything and is still just dropped, same as before.
- **Confirmed live API behavior, not documented anywhere in prose (found 2026-07-31):** a `POST /site-resource/{id}` update that omits `tcpPortRangeString`/`udpPortRangeString`/`disableIcmp` resets `udpPortRangeString` from blocked back to `*` (all) on the resource being edited, even though the swagger schema marks all three optional. `update_resource()` calls in `normalize_private_resources.py` always echo back the resource's own current values for these three fields for exactly this reason — this script never intends to touch ports/ICMP itself, the echo-back exists purely to defeat this API behavior. Don't remove it to "clean up" the payload.

## Environment

Dependencies live in the `pangolin` conda env (`/home/ktsouvalis/miniconda3/envs/pangolin`), not system/user Python. Run scripts with that env's interpreter (e.g. `/home/ktsouvalis/miniconda3/envs/pangolin/bin/python3 monitor.py`, or `conda run -n pangolin python3 ...` / after `conda activate pangolin`). If a new dependency is needed, install it into that env (`conda run -n pangolin pip install <pkg>`) — never `pip install` system-wide or `--user`.

## Testing changes

No automated tests. Verify by running against a real or representative `config.yml`, using the `pangolin` conda env:
```bash
conda run -n pangolin python3 monitor.py
conda run -n pangolin python3 logs_viewer.py
conda run -n pangolin python3 logs_viewer.py --save /tmp/test_logs
conda run -n pangolin python3 create_private_resources.py pangolin_private_resources_template.xlsx --dry-run
conda run -n pangolin python3 normalize_private_resources.py
```
`config.yml` requires live cluster network access (HTTP endpoints + SSH) to exercise fully; without it, checks will just show DOWN/UNREACHABLE, which is still useful for confirming the UI doesn't crash. `create_private_resources.py --dry-run` still needs a reachable Pangolin API + valid `api_key` (it verifies the org and lists sites/users before dry-running the row parsing). `normalize_private_resources.py` defaults to a dry run already (no `--dry-run` flag needed) — always sanity-check its report before ever passing `--apply` on the full, unscoped resource set; use `--resource-id` to try a live `--apply` against one or two resources first.
